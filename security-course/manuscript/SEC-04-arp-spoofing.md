# SEC-04 ARPスプーフィングと中間者攻撃

## この章の問い

同じLAN内で通信する端末は、IPアドレスだけではデータを届けられません。リンク層で使うMACアドレスを知る必要があります。その対応を教えるARPメッセージを無条件に信頼した場合、通信経路はどのように変わるのでしょうか。また、異常を見つけることと、不正な更新を止めることは、何が違うのでしょうか。

この章では、実ネットワークを一切使わないPythonシミュレータで、正常なARP解決、偽装主張、通信の中継、競合検知、信頼済みバインディングによる防御を順に比較します。

## 学習目標

この章を終えると、次をできるようになります。

1. ARPリクエスト、ARPリプライ、ARPキャッシュ更新の関係を説明する。
2. ARPスプーフィングが中継位置につながる成立条件を説明する。
3. 競合検知と更新拒否を、目的と結果の違いから比較する。
4. 攻撃を止めたかだけでなく、正常通信が継続したかを評価する。
5. 教材モデルで示したことと、現実のネットワークで追加確認が必要なことを区別する。

## 安全な学習範囲

この章のARPメッセージとデータフレームは、すべてPythonオブジェクトです。コードはソケットを開かず、OSのARPキャッシュを変更せず、外部ホストへ接続しません。攻撃者役も、同じプロセス内にある一つの `Host` オブジェクトにすぎません。

この制約は、単なる注意書きではありません。実装とテストの両方で、閉じた状態遷移だけを扱います。実環境でARPスプーフィングを行う手順やツール操作は、本章の対象外です。

## 1. 正常なARP解決

### 1.1 IPアドレスとMACアドレス

IPアドレスは、ネットワーク層で送信元と宛先を識別するために使います。一方、同一リンク上でフレームを届けるには、リンク層の宛先MACアドレスが必要です。送信側が宛先IPに対応するMACアドレスを知らない場合、その対応を調べる仕組みがARPです。[RFC-0826]

本章のモデルでは、被害端末 `victim` がゲートウェイ `gateway` のIPアドレス `10.0.0.1` へデータを送りたいものの、最初はゲートウェイのMACアドレスを知りません。

### 1.2 リクエストとリプライ

被害端末は、次の意味を持つARPリクエストをLAN内へ送ります。

> `10.0.0.1` を持っている端末は、自分のMACアドレスを知らせてください。

ゲートウェイは、自分のIPアドレスが問い合わせられていることを確認し、次の対応を含むリプライを返します。

```text
10.0.0.1 -> 02:00:00:00:00:01
```

被害端末は、この対応をARPキャッシュへ保存します。以後、`10.0.0.1` 宛てのデータを、MACアドレス `02:00:00:00:00:01` へ送れます。

### 1.3 この教材での単純化

ARPの実装やキャッシュ更新規則はOSや状況によって異なります。本章では、信頼の前提を観察しやすくするため、受信したARPメッセージの送信者IPと送信者MACを、更新ポリシーへ渡す単純なモデルを使います。

ここで重要なのは、「すべての実装が必ず同じように更新する」という主張ではありません。**検証されていない対応を受理する設計では、偽装された対応も状態変更の候補になる**という因果関係です。

## 2. 脅威モデル

### 2.1 トポロジ

三台は、同じインメモリLANに接続されています。

| 役割 | IPアドレス | MACアドレス |
|---|---|---|
| 被害端末 | `10.0.0.10` | `02:00:00:00:00:10` |
| ゲートウェイ | `10.0.0.1` | `02:00:00:00:00:01` |
| 攻撃者役 | `10.0.0.66` | `02:00:00:00:00:66` |

攻撃者役は、被害端末とゲートウェイの両方へARPリプライを送れます。また、自分のMACアドレスへ届いたデータを観測し、本来の宛先へ中継できます。

一方、攻撃者役には、OS設定の変更、暗号の解読、LAN外からの到達、資格情報の取得といった能力を与えません。

### 2.2 守るもの

この章で守る対象は、次の四つです。

- IPアドレスとMACアドレスの対応の正当性
- 被害端末からゲートウェイまでの通信経路の完全性
- 通信内容の機密性
- 通信サービスの可用性

中間者位置を得た攻撃者が通信を中継し続ける場合、可用性は保たれていても、経路の完全性と機密性は失われ得ます。したがって、「サービスが動いている」だけでは、安全性を判断できません。

## 3. 攻撃の成立条件

本章のシミュレータで攻撃が成立するには、次の条件が必要です。

1. 被害端末とゲートウェイが、受信したARP主張をキャッシュ更新候補として扱う。
2. 更新ポリシーが、既知の正規対応と矛盾する主張を拒否しない。
3. LANが、攻撃者のMACアドレス宛てにデータを配送できる。
4. 攻撃者が本来の宛先MACを知り、中継を有効にしている。

攻撃者役は、被害端末へ「ゲートウェイのIPは攻撃者MACに対応する」と主張します。同時に、ゲートウェイへ「被害端末のIPは攻撃者MACに対応する」と主張します。

```text
被害端末が受け取る偽装主張:
10.0.0.1  -> 02:00:00:00:00:66

ゲートウェイが受け取る偽装主張:
10.0.0.10 -> 02:00:00:00:00:66
```

この二つが受理されると、両方向のデータが攻撃者MACへ向かいます。MITRE ATT&CKでは、この種のARP Cache Poisoningを、ネットワーク上の中間者位置を得る技法として整理しています。[MITRE-T1557-002]

## 4. シミュレータを実行する

### 4.1 公開API

Notebookと本文が使う入口は、次の二つです。

```python
from conecolab_security import compare_defense, run_arp_poisoning_scenario

unprotected = run_arp_poisoning_scenario(defense_enabled=False)
protected = run_arp_poisoning_scenario(defense_enabled=True)

# 同じ順序で二条件を取得する短縮形
unprotected, protected = compare_defense()
```

各実行は `ScenarioResult` を返します。`summary()` は比較用の値、`event_rows()` は状態変化の順序を返します。本文の値は、この結果オブジェクトとテストから再現できます。

### 4.2 正常系

シナリオは、まず `baseline-message` を被害端末からゲートウェイへ送ります。被害端末のARPキャッシュが空なら、ARPリクエストとリプライが先に起こります。その後、データはゲートウェイの正規MACへ直接届きます。

正常系が成功したかは、`baseline_delivered` で確認します。正常系が失敗している状態で攻撃後の結果だけを比較しても、因果関係を判断できないためです。

### 4.3 防御なし

防御なしでは、`AcceptAllArpUpdates` が受信した主張を受理します。偽装リプライの後、被害端末とゲートウェイのキャッシュは次の状態になります。

```text
victim:  10.0.0.1  -> 02:00:00:00:00:66
gateway: 10.0.0.10 -> 02:00:00:00:00:66
```

その後、被害端末は `after-poisoning` を送ります。宛先MACが攻撃者MACになっているため、攻撃者役がデータを受け取ります。攻撃者役は内容を `intercepted_payloads` へ記録し、ゲートウェイの正規MACへ中継します。

このため、二つの結果が同時に成立します。

- `attack_succeeded is True`：攻撃者が攻撃後データを観測した。
- `service_available_after_attack is True`：ゲートウェイにも攻撃後データが届いた。

通信が止まらないため、利用者が障害だけを見ていると異常に気付きにくい、という学習ポイントが得られます。ただし、これは本シミュレータの中継条件における結果であり、実環境の検知困難性を定量評価したものではありません。

## 5. 痕跡を検知する

`ArpConflictDetector` は、各ARPメッセージの送信者主張を観測します。同じIPアドレスに対して二つ以上のMACアドレスが現れた場合、競合アラートを生成します。

正常系では、ゲートウェイIP `10.0.0.1` は正規MACだけを主張します。攻撃時には、同じIPを攻撃者MACも主張します。この組合せが、アラートの根拠です。被害端末IPについても同様に一件生成され、合計は二件です。

ARPの主張と既知の対応の不一致を監視する考え方は、MITREの検知戦略でも扱われています。[MITRE-DET0387]

### 5.1 検知だけでは止まらない

検知器はイベントを観測し、アラートを記録します。しかし、ホストのキャッシュ更新を変更しません。したがって、防御なしの実行でもアラートは二件出ますが、攻撃は成功します。

これは重要な区別です。

- **検知**：異常らしい事象を見つけ、調査のきっかけを作る。
- **防御**：不正な状態変更を拒否する、または影響を緩和する。

アラートが出たことを、攻撃を止めたことと混同してはいけません。

### 5.2 誤検知の可能性

一つのIPアドレスに複数のMACアドレスが見える状況が、常に悪意を意味するわけではありません。正当なアドレス移動、冗長化、設定変更、観測順序なども検討が必要です。IPv4のアドレス競合をARPで検出する仕組みも標準化されており、ARP主張の変化には正当な背景もあります。[RFC-5227]

本章の検知器は、このような現実の文脈をモデル化していません。したがって、アラート数をそのまま実環境の真陽性率と解釈しません。

## 6. 信頼済みバインディングで防御する

防御ありの実行では、被害端末とゲートウェイに、信頼するIP–MAC対応を設定します。

```text
victimが信頼する対応:
10.0.0.1 -> 02:00:00:00:00:01

gatewayが信頼する対応:
10.0.0.10 -> 02:00:00:00:00:10
```

`StaticBindingGuard` は、保護対象IPについて受信したMACが信頼済み値と一致するかを確認します。一致しなければ、キャッシュ更新を拒否して `arp.cache.rejected` を記録します。

この防御は、静的エントリや検査機構が守ろうとする不変条件を、初学者向けに単純化したものです。特定製品のDynamic ARP Inspectionを再現しているわけではありません。

防御ありでは、二つの偽装主張がそれぞれ拒否されます。その結果、双方のキャッシュは正規対応を維持し、攻撃後のデータは攻撃者を経由せずゲートウェイへ直接届きます。

## 7. 二条件を比較する

原型の決定的シナリオでは、次の結果になります。

| 指標 | 防御なし | 防御あり | 解釈 |
|---|---:|---:|---|
| 正常系配送 | true | true | 比較前の正常系は成立している |
| 攻撃成功 | true | false | 攻撃者による攻撃後データ観測の有無 |
| 攻撃後サービス継続 | true | true | どちらもゲートウェイへ届く |
| 競合アラート | 2 | 2 | 検知は防御条件と独立して観測する |
| 拒否したARP更新 | 0 | 2 | 防御ありだけが偽装主張を拒否する |
| 被害端末が持つゲートウェイMAC | 攻撃者MAC | 正規MAC | キャッシュの完全性 |
| 攻撃者の観測ペイロード | `after-poisoning` | なし | 経路上に入ったか |

この表から、次の三点を読み取れます。

第一に、検知数が同じでも攻撃結果は異なります。検知器と防御ポリシーの役割が別だからです。

第二に、サービス継続だけを監視しても、中間者状態を見落とし得ます。本章の防御なし条件では、攻撃者が中継するため、ゲートウェイへの配送は続きます。

第三に、防御の評価には正常系への影響が必要です。本章の固定トポロジでは、防御ありでも正常系は成功します。しかし、現実の環境でバインディングが古い、誤っている、端末が移動した、といった場合には、正当な更新を拒否する可能性があります。

## 8. 防御の副作用と限界

静的バインディングは理解しやすい一方、管理対象が増えると更新コストが高くなります。正しい対応が変わる環境では、古い設定が正常通信を止める原因にもなります。

したがって、実環境での防御設計では、少なくとも次を検討します。

- 正規対応をどこから取得し、誰が更新するか。
- 更新の頻度と監査方法。
- 例外や端末移動をどう扱うか。
- センサーがLAN内の必要な主張を観測できるか。
- 誤検知と見逃しを、どのデータで評価するか。
- 暗号化や相手認証を上位層でどう組み合わせるか。

本章の結果だけから、静的設定がすべてのネットワークに適するとは結論付けられません。

## 9. 現実のネットワークとの違い

本章は、因果関係を見やすくするため、次を省略しています。

- ARPフレームの全フィールドと厳密なタイミング
- OSごとのキャッシュ更新規則、期限、再検証
- スイッチのMAC学習、VLAN、複数ブロードキャストドメイン
- パケット損失、遅延、順序競合
- 正当なgratuitous ARP、冗長化、アドレス移動
- センサー配置と観測欠落
- 暗号化された上位層通信と証明書検証
- 製品固有の検査・ポート信頼設定

したがって、本章で示したのは、次の限定された主張です。

> 未検証のIP–MAC主張を受理するモデルでは、偽装主張によって通信経路が攻撃者MACへ変わり得る。競合の観測は異常を知らせるが、それだけでは状態変更を止めない。信頼する対応との一致を検証すれば、このモデルの偽装更新を拒否できる。

## 10. まとめ

- ARPは、IPアドレスに対応するMACアドレスを得るために使われます。
- 本章の単純な受理ポリシーでは、偽装された主張もARPキャッシュへ入ります。
- 双方向の対応が攻撃者MACへ変わり、攻撃者が中継を有効にすると、中間者位置が成立します。
- 競合検知は異常をアラートにしますが、キャッシュ更新を止めません。
- 信頼済みバインディングとの一致を確認する防御は、本モデルの偽装更新を拒否します。
- 防御の評価では、攻撃を止めたかだけでなく、正常通信と運用上の副作用も確認します。
- 教材モデルの結果を、そのまま実環境の検知率や製品性能へ一般化してはいけません。

## 演習

### 演習1：イベント列を読む

防御なしの `event_rows()` から、次のイベントを順に探してください。

1. 正常なゲートウェイ対応が保存されたイベント
2. 攻撃開始イベント
3. 被害端末のキャッシュが攻撃者MACへ変わったイベント
4. 攻撃者がデータを観測したイベント
5. ゲートウェイが同じデータを受け取ったイベント

各イベントの `sequence` と `data` を使って、因果関係を説明してください。

### 演習2：片方向だけ偽装する

`ArpPoisoningAttack.execute()` の二つの偽装主張のうち、一方だけを送る派生シナリオを考えてください。どちらの方向のデータが攻撃者へ届くか、実行前に予測してください。

実装する場合も、インメモリのクラスだけを変更し、実ネットワークへ接続しないでください。

### 演習3：検知器の基準を変える

現在の検知器は、一つのIPに複数MACを観測するとアラートを出します。次の情報を加えると、どのように誤検知を減らせるか設計してください。

- 信頼済みバインディング
- 観測した時刻またはフェーズ
- 正当な移動を示す管理イベント
- 同じ主張の継続時間

コードより先に、必要なイベントと受入条件を書いてください。

### 演習4：防御の副作用を作る

ゲートウェイの正規MACを変更したのに、被害端末の信頼済みバインディングを更新しない条件を設計してください。正常通信がどう失敗するかを予測し、「攻撃を拒否すること」と「利用可能であること」が別の評価軸である理由を説明してください。

### 演習5：現実との差を分類する

省略点を次の三つへ分類してください。

- 学習結論を変えにくい単純化
- 条件によって結論を変え得る単純化
- 次章または発展教材でモデル化すべき要素

分類理由も書いてください。
