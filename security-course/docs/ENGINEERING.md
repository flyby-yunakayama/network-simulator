# 技術設計と開発規約

## 1. 目的

この文書は、複数のAIエージェントと人間が、章ごとの実装を並行しても教材全体を壊さないための技術正本です。最優先事項は、教育上の分かりやすさ、安全境界、再現性、仕様から教材までの追跡可能性です。

## 2. アーキテクチャ原則

1. **シミュレーション専用**：実ネットワーク、OS設定、外部プロセスへ触れない。
2. **決定的**：同じ入力は同じイベント列と結果を返す。
3. **イベントを正本にする**：重要な状態変更は、順序付きの不変イベントとして記録する。
4. **正常系を先に作る**：攻撃は正常な状態遷移の一部を崩す差分として表現する。
5. **攻撃・検知・防御を分離する**：一つの巨大なシナリオ関数へ埋め込まない。
6. **安定した結果APIを返す**：Notebookや原稿が内部属性へ依存しないようにする。
7. **共通コアと教材表示を分離する**：テスト可能な実装と、章で見せる説明・差分を混ぜない。
8. **現実の完全再現を主張しない**：省略点と適用限界を仕様へ残す。

### 共通コア

`src/conecolab_security/` は、章をまたいで再利用する実行可能な正本です。将来は次の責務へ分割します。

```text
conecolab_security/
├── core/          # clock, event, phase, scenario context
├── network/       # host, link, frame, protocol state
├── attacks/       # attack orchestration; simulation only
├── defenses/      # policy, rate limit, state tracking
├── detectors/     # observation and alerts
├── metrics/       # availability, detection, latency, confusion matrix
├── scenarios/     # reproducible scenario assembly
└── presentation/  # notebook-friendly tables; no plotting side effects in core
```

現時点の `arp_lab.py` は、垂直スライスの学習価値とAPIを先に検証するため、これらを一ファイルへ集約しています。SEC-01/SEC-02で二つ以上の章が共通部品を必要とした時点で分割します。抽象化は、実際の再利用箇所が二つ以上になる前に先行させません。

### 教材スナップショット

前作は、章ごとに `sec*` の完成状態を複製することで、学習者が差分を追いやすい構成でした。次作では、次の分離を採用します。

- 実行・テストの正本：共通コア
- 章で見せる差分：Notebook、原稿中の抜粋、必要に応じた短いサンプル
- 完成コード：GitHubのタグまたは章IDに対応するコミット

同じクラスを章ごとにコピーしません。教材上どうしても段階的なコード表示が必要な場合は、生成または明示的なスナップショットとし、正本の場所を記します。

## 4. ドメインモデル

章に共通する最小モデルは次です。

| 概念 | 責務 |
|---|---|
| `ScenarioContext` | シード、時計、トポロジ、ログ、設定を保持する予定の実行文脈 |
| `SecurityEvent` | 順序、種類、主体、説明、構造化データを持つ不変イベント |
| `EventLog` | イベントの追記と参照。既存イベントを変更しない |
| Protocol message/frame | 教材に必要なヘッダと状態だけを表す値オブジェクト |
| Actor/Host | 状態を保持し、受信イベントに応じて明示的に遷移する |
| Attack | 成立条件を確認し、攻撃に対応する状態遷移を開始する |
| Detector | 観測情報からアラートを生成する。通信を止めない |
| Defense/Policy | 状態変更または通信の受理・拒否を決定する |
| Metrics | イベントと最終状態から、比較可能な指標を算出する |
| ScenarioResult | Notebook、テスト、原稿が使用する安定した結果 |

SEC-04では、`EventLog`、`ArpConflictDetector`、`StaticBindingGuard`、`ArpPoisoningAttack`、`ScenarioResult` がこの分離を示します。

## 5. 実行フロー

標準シナリオは、次のフェーズを明示的に持ちます。

1. トポロジと設定を作る。
2. 正常系を実行し、ベースラインを記録する。
3. 攻撃の成立条件を確認する。
4. 攻撃を実行する。
5. 同じ正常通信を再度実行する。
6. 検知・防御のイベントと最終状態を集計する。
7. 防御なしと防御ありを同じ条件で比較する。

フェーズ開始はイベントへ記録します。測定期間を曖昧にせず、指標がどのフェーズを対象とするか仕様で定義します。

## 6. イベント規約

### 命名

イベント種別は `domain.action.result` に近い小文字のドット区切りを使います。

例：

- `arp.sent`
- `arp.cache.updated`
- `arp.cache.rejected`
- `detector.alert`
- `data.intercepted`
- `phase.started`

### 必須情報

- 連続する `sequence`
- 機械処理用の `kind`
- 変更主体である `actor`
- 学習者向けの短い日本語 `message`
- 指標や表を作るための構造化 `data`

### 禁止事項

- ログ本文を後から正規表現で解析して指標を作らない。
- 時刻・乱数・UUIDを無条件に入れて決定性を壊さない。
- パスワード、鍵、Cookie、トークン、個人情報を記録しない。
- 同じ状態変更を、printとイベントで別々に実装しない。

## 7. 公開API

Notebookと原稿は、原則として次の層だけを呼びます。

- `run_<scenario>(...) -> ScenarioResult`
- `compare_<control>(...) -> tuple[ScenarioResult, ...]`
- `ScenarioResult.summary()`
- `ScenarioResult.event_rows()`

内部クラスを教材で見せることはできますが、Notebookの実行が内部属性へ依存しないようにします。公開APIを変更する場合は、仕様、テスト、Notebook、原稿、追跡表を同じPRで更新します。

### 結果オブジェクトの要件

- 不変または読み取り専用として扱える。
- JSONへ変換可能な要約を返す。
- 防御条件、シード、重要な設定を含む。
- 学習目標に対応する指標を含む。
- 完全なイベント列へアクセスできる。
- 表示文ではなく、意味のあるフィールド名を持つ。

## 8. 決定性

- シナリオの既定値は乱数を使わない。
- 乱数が学習上必要な場合は、ローカルな乱数生成器へシードを渡す。
- グローバルな `random.seed()` へ依存しない。
- 辞書や集合の走査順序へ結果を依存させない。
- UUID、現在時刻、プロセスIDを結果へ入れない。
- 浮動小数点比較には、仕様で許容差を定義する。
- 同じ入力によるイベント列の一致をテストする。

## 9. 安全アーキテクチャ

### 実装境界

ランタイムパッケージは、標準ライブラリのインメモリ処理を基本とします。次は既定で禁止です。

- `socket`、`ssl` を使った外部通信
- `subprocess` によるOSコマンド実行
- `requests`、`urllib`、`httpx` 等の外部アクセス
- Scapy、raw packet、pcap取得
- OSのARP、DNS、ルーティング、ファイアウォール変更

`tests/test_safety_boundary.py` は代表的な禁止importを静的に検査します。静的検査は完全ではないため、レビューでも「外部I/Oがないか」を確認します。

### 教材データ

- 予約・文書用のアドレス、または明確に架空と分かる値を使う。
- 秘密情報をNotebookへ保存しない。
- Colabの認証、Driveマウント、ユーザー環境変数を前提にしない。
- 外部サイトへ自動アクセスしない。必要な出典はMarkdownリンクとして示す。

## 10. テスト戦略

### 単体テスト

- プロトコル値オブジェクトの正規化
- 状態更新ポリシーの受理・拒否
- 検知器のアラート重複抑止
- メトリクスの境界値

### シナリオテスト

- 正常系が成立する。
- 防御なしで想定した攻撃条件が成立する。
- 防御ありで攻撃が抑止・緩和される。
- 正常通信への副作用を確認できる。
- イベント順序が再現可能である。

### 契約テスト

- `ScenarioResult.summary()` のキーと意味を保つ。
- Notebookが使用する公開APIがimportできる。
- `catalog.json` の成果物が存在する。
- Notebookに実行結果が保存されていない。

### 安全境界テスト

- 禁止importを検出する。
- 外部接続を必要としない。
- テストがローカル環境だけで完了する。

### 品質チェック

```bash
ruff check src tests examples scripts
ruff format --check src tests examples scripts
pytest
python scripts/validate_catalog.py
python scripts/validate_notebooks.py
```

## 11. Notebook設計

Notebookは、次の性質を持たせます。

- 一番上から順に実行できる。
- 出力と実行回数を消してコミットする。
- GitHubの特定タグまたはブランチからインストールする方法を示す。
- ライブラリの内部ファイルをNotebook内で再実装しない。
- 一セルの目的を一つにする。
- 結果は `summary()` または `event_rows()` から作る。
- 穴埋め課題の解答は別セルまたは講師用資料へ分離する。
- 実ネットワークへ接続しないことを冒頭で明示する。

Notebookの構造検査は `scripts/validate_notebooks.py` が担当します。将来、実行テストを導入する場合も外部通信を無効にした環境で行います。

## 12. 前作との接続

既存の `sec*` は教材資産として維持し、横断的に書き換えません。接続は次の段階で行います。

1. SEC-04の小さな独立モデルで、学習ループと結果APIを確定する。
2. 前作の `NetworkEventScheduler`、`Node`、`Switch`、`Packet` の必要な公開挙動を表にする。
3. `legacy_adapter/` のような境界層を設け、前作オブジェクトを共通イベントへ変換する。
4. 同じSEC-04受入条件を、独立モデルとアダプタモデルの両方へ適用する。
5. 教育上の差が小さく、保守負担が妥当な場合だけ移行する。

前作コードを共通コアへコピーする場合は、由来、変更点、ライセンスを記録します。

## 13. 依存関係

- ランタイム依存は、必要性が明確になるまでゼロを維持する。
- 開発依存はテスト・静的解析に限定する。
- 新しい依存を追加するPRは、目的、代替案、ライセンス、安全境界、Colab互換性を記載する。
- バージョン上限・下限は、再現性と保守性の両方を考慮する。
- 依存のネットワーク機能を使わなくても、実ネットワーク向けライブラリは原則導入しない。

## 14. 互換性とバージョニング

- `0.x` の間も、Notebookで使用する公開APIは安易に壊さない。
- 破壊的変更には、移行手順と対応する教材更新を含める。
- 章の公開版はGitタグとコミットSHAを記録する。
- 書籍の重版・改訂では、対応タグを明記する。
- 結果フィールドの削除は破壊的変更、追加は原則互換変更とする。

## 15. 章実装の標準手順

1. `catalog.json` で章IDと学習目標を確認する。
2. `CHAPTER_SPEC_TEMPLATE.md` から仕様を作る。
3. 受入条件を先にテストへ落とす。
4. 正常系の最小モデルを実装する。
5. 攻撃を別オブジェクトまたは別関数で実装する。
6. 検知と防御を分離して追加する。
7. 同一条件の比較APIを作る。
8. Notebookを公開APIだけで作る。
9. 原稿で結果を解釈し、現実との差を示す。
10. `TRACEABILITY.md` と出典台帳を更新する。
11. すべての検証を通す。

## 16. 設計判断の記録

重要な判断は `DECISIONS.md` へ追加します。記録には、状況、判断、理由、結果、再検討条件を含めます。実装から推測しなければならない重要設計を増やさないことが、AIエージェントの誤変更を防ぎます。
